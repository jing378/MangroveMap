# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

MangroveMap is a Laravel 13 (PHP 8.3) app for mapping mangrove areas (Southern Leyte, PH). Users draw delineation polygons on a Leaflet map, experts review them, and drone orthomosaics are tiled with GDAL, segmented with a PyTorch U-Net and classified by canopy with a YOLO model. It runs locally under Laragon on Windows, with MySQL in `.env`. Tests use in-memory SQLite.

## Commands

```powershell
composer dev                      # serve + queue:listen + pail logs + vite, concurrently
npm run dev / npm run build       # Vite + Tailwind 4
composer test                     # config:clear, then php artisan test
php artisan test --filter=DroneImageryUploadTest          # single test class
php artisan test --filter=test_method_name                # single test method
php artisan test tests/Unit/BoundaryResolverTest.php      # single file
vendor/bin/pint                   # format (Laravel Pint)

# Drone imagery needs its own worker (composer dev's queue:listen does NOT cover it)
php artisan queue:work drone_imagery --queue=drone-imagery --timeout=7200 --tries=1
# queue:work keeps the code it started with: restart this worker after changing jobs/services it runs

php artisan boundaries:import --path=<geojson>   # load barangay boundaries into admin_boundaries
php artisan delineations:repair-features --dry-run
php artisan delineations:resolve-locations --dry-run [--id=N]   # fill in barangays for areas not matched yet
php artisan map:sync-place-labels                # re-download OpenStreetMap place names for the satellite map labels
```

ML environment: `ml/.venv` (from `ml/requirements.txt`). `config/ml.php` automatically uses `ml/.venv/Scripts/python.exe` if it exists. Otherwise set `ML_PYTHON`.

## Architecture

### JSON endpoints
All routes are in `routes/web.php` (session auth + CSRF, for MangroveMap's own pages); there is no `routes/api.php` or token API. `docs/API.md` documents the JSON endpoints, their roles, bodies, responses and rate limits. Update it when you add or change one. Give every route throttle its route name as the third argument (`throttle:20,1,drone-imagery.uploads.complete`): a plain `throttle:N,1` counts on one counter per user shared by all such routes, so a big drone upload's chunks used to make `complete` (and the notification poll) return 429.

### Roles and routing
`users.role` is `end_user` (resident), `expert`, or `admin`. Route groups in `routes/web.php` use the `end_user`, `expert`, and `admin` middleware aliases (`app/Http/Middleware`). `User::homeRoute()` decides where each role lands after login or verification. Shared map/delineate pages (`EndUserController::map/delineate`) serve all authenticated users. Experts get their own variants under `/expert/*` in `ExpertController`.

Admin dashboard (`AdminController::dashboard`) shows only real data: users, approved hectares (`ApprovedCoverageStats`), the expert review queue, drone imagery status, the AI models in use (`aiModelStatus`: newest active uploaded model, else the default file in `ml/models`) and a "Needs attention" list (missing model, failed drone layers, expert applications, pending delineations older than `STALE_REVIEW_DAYS`, new feedback). Three overview charts follow, as plain HTML bars that link into Map Layers (no canvas, so they theme like the page): the drone survey pipeline by stage (`droneStageCounts`), delineation reviews as one stacked bar with the average review time over `REVIEW_TIME_DAYS` (experts' own auto-approved areas left out) and the hand-drawn/drone split (`reviewStatus`), and approved hectares by municipality, top `CHART_MUNICIPALITIES` then "Other" (`hectaresByMunicipality`). Their review colours were checked for colour-blind separation in both themes; keep the teal-leaning green and the dark-mode amber if you change them. Admin Map Layers (`MapLayerController`) has two tabs, Delineations (with municipality, barangays, hectares, genera) and Drone Surveys (the drone imagery layers). Previews of both draw the drone imagery from `MapLayerController::imageryPreviewAttributes`: map tiles once a layer is ready, else the review image (`drone-imagery.preview`, which admins may fetch) while it awaits its owner's review and has no tiles yet; the imagery and its delineation are always shown together (a delineation drawn from drone imagery, pending ones included, on that imagery; a drone layer with its submitted delineation, or the AI-detected extent before it has one), and the rows link to each other (`?delineation=ID` / `?tab=imagery&layer=ID` open that one record). It exports the current tab as CSV (`admin.map-layers.export`, every row matching the search/status) or delineations as GeoJSON (`format=geojson`, polygons in [lng, lat], published ones unless a status is chosen). Tabs, the filter, pages and the cross-links do not reload the page: `map-layers-scripts` fetches the URL and swaps only the list card (`#layerList`), updating the address bar (back/forward work); row buttons there are delegated, so keep new ones delegated too. Clicking a row (or Enter/Space on it) shows it on the preview map; there are no preview buttons. Admin row actions are only cleanup: Delete on delineations, and on imagery Retry processing (failed layers only; owners have no retry) and Delete. Naming, review, edits and re-running the AI stay with owners and experts, so admins have no hide, edit, rename or re-segment (the `hidden_*` columns were dropped). The imagery tab's Stage column and filter come from `DroneImageryLayer::stage()` / `scopeInStage` (`STAGES`: processing, AI detecting, waiting for owner, finalizing, pending expert, rejected, published, ready but not submitted, failed; the "failed" filter also covers failed AI steps). AI areas are only a draft until the owner confirms them, so they never appear on the Delineations tab; a layer waiting for its owner over `STALE_DRAFT_DAYS` (7, from `segmented_at`, else `created_at`; `scopeStaleOwnerDraft`) is shown in amber, counted in the "Waiting for Owner" card and listed in the dashboard's "Needs attention". Each delineation row is labelled by `delineations.source` (`Delineation::SOURCES`: `manual` "Hand-drawn", `drone` "Drone survey (AI-assisted)", set by `DroneImageryDelineationPublisher`; an admin deleting a drone survey deletes its delineation too (`destroyImagery`, owner notified), so only records from before that show "imagery deleted"; older records were backfilled from the layer link, the default drone notes and the "Deleted drone imagery: <name>" activity log), with a Source filter that the CSV/GeoJSON exports follow; a drone one links to its imagery and shows that layer's stage when it adds to the row's status (Finalizing, Failed, ...). Row actions (POST) still reload and restore the scroll position. The preview map has an expand button (full-window overlay, Esc closes). The former Datasets page was merged into it; `/admin/datasets` redirects there. The old `mangrove_data` / `analysis` demo tables are no longer shown anywhere in the admin.

Admin reminders (`AdminReminderController` → `App\Services\AdminReminderSender`, notification `ReminderFromAdmin`: bell, email, push): "Send reminder" on the dashboard's overdue-review and stale-AI-draft "Needs attention" items (`pending_reviews` → every expert; `stale_drafts` → each owner once, naming their surveys), and a bell in Map Layers rows (`delineation` → experts about one pending delineation; `drone_layer` → the owner of a survey waiting for them). They open the shared `admin.partials.reminder-dialog` (optional note; openers carry `data-reminder` + `data-reminder-kind`/`-target`, delegated so swapped lists work). Each send is stored in `admin_reminders` (`AdminReminder`) and logged; the same kind + target goes out at most once per `AdminReminder::COOLDOWN_HOURS` (24), and the button then shows "Reminded … ago".

Login status (admin Users page and user details): on the admin pages "Active" means only a live login session, from rows in the database `sessions` table (`User::loggedInNowIds`; empty with any other session driver). Logging out deletes the row; closing the browser leaves it until `SESSION_LIFETIME` (120 min) passes. Everyone else shows "Last seen …" from `users.last_seen_at` (written by `TrackUserPresence`, appended to the `web` group, at most once a minute) or `last_login_at` (`User::loginStatusLabel`). Email verification is "Verified" / "Not verified", never "Active".

### Delineation lifecycle
`Delineation` stores GeoJSON in the `features` JSON column. Review state is tracked by the `is_approved`/`is_rejected` flags (there is no status enum). The flow is:
1. A resident submits a delineation. `DelineationSubmittedForReview` notifies experts.
2. An expert approves or rejects it. A resident can revise a rejected record (`delineations.revise`), and revisions are kept in `DelineationRevision`. The resident has `Delineation::REJECTED_REMOVAL_GRACE_DAYS` (7) from `rejected_at` to do so. After that an expert may delete it. Experts can delete approved and pending delineations at any time (`expert.delineations.destroy` → `ExpertController::destroyDelineation`; `DelineationRemoved` notifies the owner unless it is the expert's own). A resident can delete their own pending or rejected delineation (`delineations.destroy`, never an approved one); `DelineationWithdrawn` then tells the experts: every expert for a pending one, the expert who rejected it (`rejected_by`, else all) for a rejected one. The rejection notice, map panel and dashboard show the deadline (`removable_after` in the map payload).
3. Experts can also add yearly observations and planting recommendations (`PlantingRecommendation`). There is no separate observation form. When an expert saves a boundary edit (`delineations.boundary.update`) with `record_as=observation`, `DelineationObservationRecorder` creates or updates that year's `DelineationAnnualObservation`, with hectares computed from the polygon, genera taken from the features, and a boundary revision. The first observation also stores a baseline year from the original boundary. A `record_as=correction` edit (the default) only adds a `DelineationRevision`. While editing a boundary, experts and residents (own pending records) can also add a shape to the same delineation ("Draw a new area", `boundaryEdit.addingArea` in `workspace-scripts`, drawn as an open line like on the Delineate page until it is closed; map clicks are gated by `isDrawingLocked()`); it is sent with the other shapes on save and dropped on Cancel. "Remove selected area" takes a shape out (`removed_in_boundary_edit`: hidden and left out on save, restored by Cancel or Undo; at least one area stays). A resident's "Revise rejected delineation" has the same two buttons (`.area-edit-add` / `.area-edit-remove` with `data-area-edit="boundary|revision"`; `areaEditMode()` / `shapeEditFeatures()` work on whichever edit is active). `DelineationAnnualObservationController::index` is read-only and feeds the map's "Changes over time" timeline.

Deleting a delineation also removes its review notifications (a model `deleting` hook). Map queries are capped by `Delineation::MAP_QUERY_LIMIT*`.

`BoundaryResolver` reverse-geocodes polygons to barangay/municipality using MySQL spatial functions against `admin_boundaries`. On SQLite, or when the table is empty, it skips the lookup and does nothing. Tests therefore run without spatial data.

### Live notifications
`partials/live-notifications` (both layouts) asks `notifications.poll` every 20 s while the tab is visible (paused when hidden, immediate check on return, backs off on errors, stops on 401/419). The answer is the unread count plus notifications created since the previous answer's `now`. It updates the sidebar bell badge (the mobile menu dot follows it) and shows each new one as an `AppActions.notify` toast with title, icon and a View link (`notify` options `icon`, `title`, `action`). On the Notifications page it shows a "N new notifications · Show" bar instead, since cards there carry server-rendered actions. It also fires a `live-notifications` DOM event: on Map/Delineate, a `delineation_*` notification re-downloads the delineations (`refreshMapKeepingView` in `workspace-scripts`, also the map-controls refresh button), keeping the view, selection and open panel. While the user is busy (drawing mode, unsaved drawings, boundary edit/revision, saving, rejection notes) it waits, shows the `mapUpdateChip`, and runs once they're idle. Phones also get pull-to-refresh (`partials/pull-to-refresh`, skipped on map pages).

### Device notifications (Web Push)
Every notification also pops up on the user's phone/computer when they turned it on for that browser (card at the top of the Notifications page, `partials/device-push`; `PushSubscriptionController`, table `push_subscriptions` via `laravel-notification-channels/webpush`'s `HasPushSubscriptions` on `User`). `NotificationChannels::databaseAndMail($notifiable)` / `::push($notifiable)` add the `webpush` channel only when the VAPID keys are set in `.env` and the user has a subscription. That channel is `DevicePushChannel` (registered in `AppServiceProvider`): it builds the push from the notification's `toArray()` (title, message, and a link resolved like the bell's "View"), so new notifications get push for free. A failed push is logged and never breaks the request. `public/sw.js` shows it and opens the link on tap. Logging out removes that browser's subscription (endpoint kept in the session), but the choice is remembered per account in the browser (localStorage `mangrovemap.push.wanted`, set/cleared by the card): `partials/device-push-restore` (both layouts, only while the session has no `push_endpoint`) subscribes again without a prompt when that user logs back in and the permission is still granted. Needs HTTPS; on iOS only from a Home Screen install (16.4+). On Windows, PHP's OpenSSL needs `C:\Program Files\Common Files\SSL\openssl.cnf` (copy of `<php>\extras\ssl\openssl.cnf`) or every push fails with "Unable to create the local key".

### Drone imagery pipeline
1. The Drone Upload page uploads through `DroneImageryUploadController` in chunks: `start` creates a session in `drone-imagery/incoming/{uuid}`, the browser PUTs 8 MB slices (`gdal.upload_chunk_mb`) four at a time (`gdal.upload_parallel`) with retries, each written straight to its offset in a `.part` file, and `complete` moves the parts into place. The session id is kept in localStorage, so picking the same files again resumes. Abandoned sessions are removed after 24 h (`drone-imagery:prune-uploads`, scheduled daily). `DroneImageryController::store` (one multipart request) still works. Both create a `DroneImageryLayer` plus its `DroneImageryFile` rows and call `queueProcessing`.
2. `ProcessDroneImagery` runs on the `drone_imagery` connection and `drone-imagery` queue. It runs GDAL through `GdalCommandRunner`, which writes a `.bat` file that first calls the QGIS `o4w_env.bat` (`GDAL_QGIS_ENV`). This step builds the mosaic and XYZ tiles. A batch is one mosaic, so before warping it fails the layer when its files come from places far apart (e.g. Macrohon + Bontoc): `DroneBatchFootprints` groups the files' footprints within `gdal.batch_max_gap_m` (1000 m) and names each group's municipality when boundaries are loaded. The Drone Upload page runs the same check before uploading (`drone-upload-scripts`: geotiff.js reads each file's header, footprints converted from EPSG:4326/3857, UTM WGS 84 and PRS92/Luzon 1911 zones; other CRSs skip it and rely on the job). The max zoom is chosen automatically from the raster's native resolution (see `config/gdal.php`).
3. If `ML_DRONE_AUTO_SEGMENT` is on, it dispatches `SegmentDroneImagery`. That job resamples the mosaic and calls `MangroveSegmentationService::predictExtent`, which picks the extent model (`ML_DRONE_EXTENT_MODEL`, default `unet`): the U-Net (`ml/predict.py --raster`), or with `yolo` the YOLO canopy model (`ml/predict_genus.py --extent-out`, the union of every canopy found at `ML_YOLO_EXTENT_CONFIDENCE`), which falls back to the U-Net when its weights are missing or the run fails. `SegmentationFeatureBuilder` then turns the mask into simplified GeoJSON polygons, which are offered as a delineation draft. `segmentation_stats.extent_model` records which model drew it. That is all it does (the AI delineation): when the areas are ready it queues `ClassifyDroneImagery` (`ClassifyDroneImagery::queueFor`, skipped without genus weights), and a new delineation run first clears the old genus results.
4. Review and publication: the owner corrects the mangrove areas in the review editor, then confirms. The first confirm also requires the genus (`delineation_details`). When `FinalizeDroneImagery` has tiled the layer, `DroneImageryDelineationPublisher` turns those areas into a `Delineation` linked by `drone_imagery_layer_id`. A resident's delineation starts pending and experts are notified; an expert's is approved immediately. A layer is `published()` once it is ready and either its owner is an expert or its delineation is approved. Until then, only the owner and experts can see it (`awaitingExpertReview()`). The map shows `auto_show` layers without anyone ticking them.
   Re-surveys: when the saved areas overlap approved delineations (`DelineationReassessment::candidatesFor`, PHP geometry, so it works on SQLite too), the review editor's Details offer "Survey of": a new area, or a re-survey of one of them (`delineation_details.reassesses_delineation_id`, checked again on confirm and when publishing). The survey still gets its own delineation (so the layer's review state works as usual), linked by `delineations.reassesses_delineation_id`. When it is approved (`ExpertController::approve`, or at once for an expert's), `DelineationReassessment::apply` copies its boundary onto that area as a `reassessment` revision plus that year's observation ("Drone imagery"), keeping the area's name and owner; the owner gets `DelineationReassessed` (old → new hectares) unless they flew or approved it. An approved re-survey (`isAppliedReassessment()`) is then left out of the map payloads, the landing page, planting reference areas, the GeoJSON export and `ApprovedCoverageStats` (`scopeWithoutAppliedReassessments`), so its hectares count once; links to it open the area it updated. Deleting the original turns its re-surveys back into areas of their own.
5. Tiles and segmentation are served only through owner-authorized routes (`drone-imagery.tile`, `.segmentation.show`). Nothing is public via the storage symlink. Users can hide layers (`drone_imagery_layer_hidden_users`). The map's Drone Imagery panel (`map-base-scripts`) only lists layers with their status, View (show and zoom) and Delete (the owner) or Remove (hide someone else's); reviewing, editing and the AI overlays live on Drone Upload and in the review editor. When the owner deletes a layer (`drone-imagery.destroy`, from the map's Drone Imagery panel or Drone Upload), its delineation is deleted too, even an approved one. For a resident's layer, experts get `DelineationWithdrawn::notifyExperts` (shared with `delineations.destroy`).

Tile Explorer (sidebar, `TileExplorerController`): users upload a single GeoTIFF to cut it into tiles for dataset work (e.g. Roboflow). It is private to the uploader and never becomes a map layer or delineation by itself; "Send to Drone Imagery" in the selection bar (`tile-explorer.sets.drone-imagery` → `TileExplorerController::sendToDroneImagery`) copies the selected tiles' GeoTIFFs into a new `DroneImageryLayer` (one batch) and calls `queueProcessing`, so it then follows the normal drone pipeline and review on Drone Upload. The upload reuses the chunked uploader (`DroneImageryUploadController` with `purpose=tiles` and `tile_size`; the browser client is `partials/chunked-upload`). It creates a `TileSource` (`tile-explorer/{id}/source.tif`, kept as uploaded) and a `TileSet` per tile size. `GenerateTiles` (drone imagery worker/queue) validates it (8-bit RGB with a CRS). On the first run per source it detects mangrove areas with `MangroveAreaDetector`, the extent model via `predictExtent` on a working copy warped to EPSG:3857, saved as `areas.geojson`; if this fails, tiles are still made, unlabelled. It then runs `scripts/gdal/make_tiles.py` on the original file in its own CRS. Per tile that writes a GeoTIFF, a JPEG plus `.wld`/`.aux.xml`, and a thumbnail, named by id `r<row>_c<col>` under `tiles/{size}/`, plus `tiles.json` (mangrove % per tile and an SVG outline). Fully empty tiles are skipped. Downloads are GeoTIFF only: one selected tile is sent as its `.tif`, two or more as a ZIP of just the `.tif` files (the JPEGs stay for the page's previews). The ZIP streams with `maennchen/zipstream-php` (no ext-zip, no temp file) and sets the unencrypted `tile_download_token` cookie so the page knows the download started.

Keep `GDAL_QUEUE_RETRY_AFTER` (7260) above the job timeout (7200). Above that, `GDAL_PROCESS_TIMEOUT` (7000) caps each GDAL command.

### ML integration
`MangroveSegmentationService` shells out to `ml/predict.py`. The script has three modes, `--image`, `--raster`, and `--validate-weights`, and prints JSON as its last stdout line. The weights come from the newest active `AIModel` (`model_type=segmentation`, a `.pth` file that exists on disk). If there is none, it falls back to `ML_MODEL_PATH`. Admins upload new models via `AdminController::uploadModel`, which validates them first, deactivate the active one (`admin.models.deactivate`: the green check in the row; new runs then use the default file in `ml/models`), and delete one from the registry (`admin.models.destroy` → `destroyModel`: removes the record and its file, but only files in the storage `models/` upload folder; deleting the active model leaves the pipeline on the default file in `ml/models`). Under Apache on Windows, the service and the script both patch `SystemRoot`/`PATH`. Without that, importing torch fails with WinError 10106. Keep those workarounds. For the same reason (Apache on Windows runs PHP in threads that share one environment), `public/index.php` calls `Env::disablePutenv()`: without it, parallel requests such as Tile Explorer thumbnails randomly fail as "production" with "No application encryption key".

Genus suggestion and canopies (the genus classification) are a separate job, `ClassifyDroneImagery` (same worker/queue), with its own columns: `classification_status` (null/queued/processing/ready/failed), `classification_stats` (`genus_suggestion`, `canopy_count`, `canopies_by_genus`, the raster `offset` the canopies sit at), `classification_error`, `classified_at`. Payloads still show those three keys inside `segmentation_stats` (`DroneImageryLayer::aiStats`); copies stored there before the split are ignored. It resamples the mosaic exactly like `SegmentDroneImagery` (shared trait `PreparesAiRaster`) and runs `ml/predict_genus.py --areas` (an Ultralytics YOLO segmentation model, classes = genera), counting only pixels inside the layer's current mangrove areas from `ai_extent.json` (AI-drawn or the owner's corrections), so the owner can edit the areas while it runs; if they save new areas meanwhile, it recounts for those at the end. The owner can re-run it alone (`drone-imagery.classification.store`, "Re-run genus detection" in the review editor) without touching the areas. Each detection is one canopy: those inside the areas are saved as `canopies.json` in the layer's processed folder (genus, confidence, area, centre, outline; `--canopies-out`, capped by `ML_CANOPY_MAX`), served by `drone-imagery.canopies.show` and shown as genus-coloured pins (outlines when zoomed in) in the review editor. `canopy_count` / `canopies_by_genus` summarise them. The suggestion is `genus_suggestion` (`{error}` on failure, which never touches the areas). The review editor shows it as one clickable list ("AI genus suggestion": a probability for every genus, tagged Confident/Low confidence) and never selects a genus by itself. The job also keeps a per-pixel genus map (`genus_labels.png` + `.json` in the layer's processed folder); when the owner saves edited areas, `updateSegmentation` recounts the suggestion from it (once the classification is ready) (`predict_genus.py --recount`, no model run, under a second). While editing, the review editor also previews it live: 0.8 s after each area change it posts the unsaved areas to `drone-imagery.segmentation.genus-preview`, which recounts without saving. Layers processed before the map existed keep their original suggestion until the genus detection is re-run. Weights come from the newest active `AIModel` with `model_type=classification` (a `.pt`, uploaded by admins), else `ML_GENUS_MODEL_PATH` (`ml/models/mangrove_classifier.pt`). Settings are in `config/ml.php` under `genus`.

### Frontend
Blade views with Leaflet 1.9.4 from a CDN. Satellite basemaps get Google-hybrid-style labels from `partials/map-place-labels` (`attachPlaceLabels(map, imageryLayers)`): Esri roads plus OpenStreetMap place names from `OsmPlaceLabelService` (Overpass, stored in `storage/app/private/map/`, bbox in `config/map.php`, decluttered client-side by rank). Most map code is inline JS in Blade partials under `resources/views/users/partials/` (`workspace-*`, `map-base-scripts`, `recommendation-scripts`), not in `resources/js`. Layouts: `layouts/enduser`, `layouts/admin`, `layouts/app`.

Year slider (map page, the graph button in the map controls): the satellite "Mangrove extent by year" below is hidden for now (`map.mangrove_history.enabled`, env `MAP_MANGROVE_HISTORY_ENABLED`, default off). While it is off, the same card (`users/partials/mangrove-history`) is driven by `map-timeline-scripts` as "Mangroves mapped by year", from the system's own records: hectares per year are the Coverage Trend (`ApprovedCoverageStats`), and the map keeps only the delineations, pins and drone layers created up to the chosen year (`mapTimelineYear` in `workspace-scripts`; drone layers via `window.onDroneImageryLayers`). The dashboard's satellite chart is hidden too.

Mangrove extent by year (when enabled): where satellites mapped mangroves in each year from 1985 to 2025, from Global Mangrove Watch v4.1 (about 30 m, CC BY 4.0). `resources/data/mangrove-history.json` holds it for Southern Leyte as runs of pixels with their years as bits, plus hectares per year for the province and each municipality. `MapMangroveHistoryController` serves it (public, gzipped) and `users/partials/mangrove-history` + `mangrove-history-scripts` draw it on a canvas grid layer with a year slider, play button, hectares chart and a gained/lost comparison between two years. It is separate from an area's "Changes over time" (expert observations). The resident/expert dashboard charts the same hectares per year (`MangroveHistoryStats`, with a municipality picker) beside its Coverage Trend, which stays approved delineations only. To rebuild the file, download the four GMW tiles (N10E124, N10E125, N11E124, N11E125 from `gmw_mng_ext_v4112_stack.tar.gz`, doi:10.5281/zenodo.21346456), export the barangay boundaries as GeoJSON, and run `scripts/gmw/build_mangrove_history.py` with the QGIS Python.

Dashboard report (resident and expert dashboard), kept visual rather than wordy: "Mangrove Report" is hidden until the "Total Monitored Area" card is clicked (it opens below the cards; open/closed remembered per browser, `#municipalityReport` opens it). It counts only expert-approved areas (`approved()`, not rejected) from `ApprovedCoverageStats` `by_municipality`: a Chart.js histogram (one column per municipality, hectares; drawn the first time the panel opens) over a table (municipality, hectares, share, area count, total row; Share hides on phones). Tapping a column or a row opens that municipality's areas one by one in the table (`areas`: name, barangay, hectares bar, map link to `map?delineation=id`, plus `map?municipality=Name`, which opens the map year card on that place). CSV download (client-side) of every municipality: totals, then each area. "Mangrove Types (Genus)" is one coloured bar per type (local name first, share of approved areas); tapping one shows how to recognise it (`App\Support\MangroveGenera`).

Loading feedback: `partials/nav-progress` (both layouts) shows a thin bar at the top when a link or normal form submit takes over 300 ms to load the next page; mark anything that must not start it with `data-no-progress` (new tabs, `download` links, `#` links and forms that `preventDefault` are skipped already). `map-base-scripts` covers the map with "Loading map…" until the first imagery tiles load (12 s at most).

Dark mode: `partials/theme` (included first in every page `<head>`) sets `<html data-theme="light|dark">` from localStorage or the OS setting, and `partials/theme-toggle` is the header button. View CSS colors are written as `var(--bg-xxxxxx, #xxxxxx)` (prefix `bg`/`fg`/`bd` = role); light mode uses the fallback and the dark values live in the generated `partials/theme-palette`. After adding styles with literal colors, run `node scripts/theme/build-dark-theme.mjs` (`--check` lists views that still need it). It skips `<script>` blocks and `--custom-properties`, so colors in JS-built HTML or page-level CSS variables need a dark value by hand (see the `html[data-theme="dark"]` block in `index.blade.php`).

## Testing notes
- `phpunit.xml` sets SQLite `:memory:`, `QUEUE_CONNECTION=sync`, and array mail/cache/session.
- `ProcessDroneImageryTest` runs real GDAL through the QGIS install. If `gdal.qgis_env` doesn't exist, it skips itself.
- Segmentation tests write segmentation output directly and use `Queue::fake()`, so Python isn't needed.
